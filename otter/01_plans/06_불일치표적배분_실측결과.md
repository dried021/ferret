# §6 "불일치-표적 calibration budget 배분" 실측 결과 및 원인 분석

작성: 2026-07-28 (실측 완료 직후 정리). 대응 설계 문서: `00_docs/06_논문_구성.md` §6.
관련 코드: `scripts/scan_disagreement_experts.py`(Stage 1), `scripts/phase1_6_targeted_budget.py`(Stage 2),
`scripts/phase1_6_budget_gate.py`(Table 3 게이트, 사전등록).

## 결론 먼저

**두 변형(무제약 / cap50) 모두 §6에 사전등록된 유일한 게이트 기준("Balanced를 이기지 못하면
기여를 주장하지 않는다")을 통과하지 못했다 → `NOT_SUPPORTED`.**

원인은 구현 버그가 아니라 방법론 설계 자체의 문제로 보인다: Stage 1의 "라우팅 불일치" 프록시가
측정하는 것(=이 언어가 이 전문가에 얼마나 안정적으로 샘플링됐는가)과, 실제로 문제인 것
(=이 언어가 압축 후 얼마나 나빠지는가)이 이 실험 조건에서는 상관관계가 약하거나 반대 방향이다.

## 1. 실행 내역 (실제로 무엇을 돌렸는가)

- Stage 1: `scan_disagreement_experts.py` 실측 스캔 완료 (27개 MoE 레이어 × 6 조건: english/chinese/
  korean/swahili/bengali_only + balanced, forward-only proxy, 근사 — Fisher 최종 결과에는 사용 안 함)
- Stage 2: `phase1_6_targeted_budget.py`로 두 배분안 계산
  - **무제약(uncapped)**: `--target-hit-count 20 --floor-share 0.05` (max_share 없음)
  - **cap50**: 동일 + `--max-share 0.5` (2026-07-27 코드 리뷰에서 "단일 언어가 예산을 독식하는
    구조적 편향" 우려로 추가된 변형)
- **실제 압축/평가는 real gradient Fisher만 사용** (forward-only proxy 아님) — `phase1_fisher.py`
  (`--n-samples 64 --seqlen 512`, 다른 모든 조건과 동일 예산) → `phase1_merge_eval.py` (plain SVD,
  whitening off, 프로젝트 기본 컨벤션과 동일)
- 두 배분안 × seed {0,1,2} = 6개 조합 전부 완주, 에러 없음
- 비교군 Balanced(`mixed_5lang`, EN/KO/ZH/Swahili/Bengali 균등 20%씩)도 seed 0/1/2 신규 실행
  (기존 3언어 `balanced`는 Swahili/Bengali를 본 적이 없어 비교 불가 — 재사용 안 함)

| 언어 | Balanced (기준) | 무제약 | cap50 |
|---|---|---|---|
| English | 0.200 | 0.050 | 0.050 |
| Korean | 0.200 | 0.050 | 0.050 |
| Chinese | 0.200 | 0.050 | 0.050 |
| Swahili | 0.200 | **0.732** | 0.500 |
| Bengali | 0.200 | 0.118 | 0.350 |

Swahili=31, Bengali=5, English/Korean/Chinese=0 → 스와힐리가 압도적 "표적"으로 지목됨.

## 4. 원인 분석 (재현 가능한 데이터 근거)

### 4-1. Swahili에는 예산을 더 줄수록 실제로 도움이 됐다
언어별 표에서 Swahili는 Balanced(20%) → cap50(50%) → 무제약(73%)로 갈수록
19.50 → 17.06 → 15.41로 꾸준히 개선. 즉 프록시가 "표적"으로 고른 언어에 대해서는
예산-성능 관계가 방향은 맞다.

### 4-2. 그런데 Bengali는 프록시가 애초에 "문제없음"으로 판단했다
deficiency(Bengali)=5/810 pairs로 매우 낮음 — 균등분배(20%)만 해도 대부분의 불일치 전문가에서
hit_count≥20을 이미 만족한다는 뜻. 그래서 무제약은 Bengali 예산을 Balanced보다도 줄여버렸다
(11.8%). 이 경우 Bengali가 나빠지는 것은 예측 가능한 결과다.

### 4-3. 결정적 반증: cap50은 Bengali에 Balanced보다 *더 많은* 예산(35%>20%)을 줬는데도 여전히 졌다
이게 핵심 반증이다. 단순히 "Bengali 예산이 부족해서" 문제라면 cap50에서는 해결됐어야 한다.
그런데 cap50의 Bengali 결과(22.81%)는 Balanced(22.03%)보다 오히려 미세하게 더 나쁘다.
→ 문제는 "얼마나 줬냐"가 아니라 "어떤 전문가에 집중해서 줬냐"에 있다. 무제약/cap50 모두
calibration 텍스트의 언어 *비중*만 바꿨을 뿐, "표적 전문가 집합"(Stage 1이 고른 disagreement
experts)는 Swahili 중심으로 뽑힌 것이므로, Bengali 문장 비중을 늘려도 그 문장들이 실제로
Bengali에 중요한 전문가의 Fisher 추정을 개선하는 방향으로 작동하지 않았을 가능성이 높다.

### 4-4. Bengali는 애초에 "예산과 무관하게" 압축에 더 취약한 언어다
단일언어 조건(자기 언어에 calibration 예산 100% 전량 투입 — 이론상 최선의 케이스)을 비교하면:

| 조건 | 자기 언어 bpb 증가율 (3-seed 평균) |
|---|---|
| `bengali_only` (Bengali 100%) | Bengali: **17.5~17.8%** |
| `swahili_only` (Swahili 100%) | Swahili: **12.8~13.5%** |

100% 전량 투입이라는 이론적 최댓값에서도 Bengali의 최선의 결과(~17.7%)가 Swahili의 최선의
결과(~13%)보다 훨씬 나쁘다. 즉 Bengali는 calibration 예산 배분 전략과 무관하게 원래 이
압축 파이프라인(Fisher 병합 + plain SVD)에 더 취약한 언어다.

### 종합
Stage 1의 "라우팅 불일치(routing disagreement)" 프록시는 "이 언어가 이 전문가에서 충분한
calibration 샘플을 확보했는가(데이터 커버리지)"를 측정하는 지표이지, "이 언어가 압축 후
실제로 얼마나 나빠지는가(압축 취약성)"를 측정하는 지표가 아니다. 이 실험에서 두 지표는
상관관계가 약하거나(§4-3) 반대 방향(§4-2, 가장 취약한 언어가 가장 낮은 deficiency로 잡힘)이었다.

## 5. 남은 이슈 (본 결과의 결론에는 영향 없음)

- Table 3의 "최선 단일 언어" context 비교는 `english_only`/`korean_only`/`chinese_only`/
  `swahili_only`의 예전 `eval_ppl.json`에 `ben_Beng` 키가 없어(벵골어 추가 이전 실측) 아직
  계산 못 함 — 게이트 판정 자체는 Balanced 비교만으로 이미 확정되므로 gating에는 영향 없음.
  필요 시 해당 4개 조건 재평가(merge 재사용, eval만 재실행)로 간단히 채울 수 있음.
- Ablation (i) random-expert targeting, (ii) real-Fisher 기반 Stage 1, Figure 5 budget-curve
  스윕은 모두 미착수 (원래 §6 스펙에 있던 항목, 우선순위상 이번 원인 분석 이후로 보류).
