# 13. FERRET Toy0 방법론 — 단일 RTX 3090 (v1.0)

## 0. 목적

이 문서는 24GB VRAM을 가진 단일 NVIDIA RTX 3090에서 실행 가능한 FERRET Toy0
실험을 정의한다.

FERRET의 핵심 가설:

> 같은 MoE 전문가로 라우팅된 토큰들 사이에서도, 모델 동작을 보존하는 데 필요한
> 최소 전문가 랭크(rank)는 서로 다르다.

따라서 Toy0는 FERRET 시스템 전체를 구축하려 하지 않는다. **토큰별 동적 랭크
할당이 정적(static) 랭크 할당보다 오라클(oracle) 관점에서 우위를 갖는지**만
검증한다.

**최소 성공 조건**

```
Oracle 토큰별 랭크 할당 > 최선의 전문가별 정적 랭크 할당
```

동일한 평균 실행 랭크(또는 근사적으로 동일한 이론적 전문가 FLOPs) 조건에서.

예측기 학습, 커스텀 커널, 실제 지연시간 최적화, 전체 모델 압축은 Toy0 범위에서
제외한다.

---

## 1. 단일 GPU 실행 전략

단일 RTX 3090으로는 다음 워크플로우를 효율적으로 지원할 수 없다.

- 매우 큰 MoE 모델을 FP16으로 전체 로드
- 모든 레이어의 모든 전문가를 분해
- 라우팅된 모든 토큰의 활성화(activation)를 저장
- 전체 모델 forward pass를 반복하여 모든 후보 랭크를 평가

대신 Toy0는 **2단계 오프라인 재생(replay) 설계**를 사용한다.

**Stage A: 라우팅 트레이스 수집**
원본 모델을 소규모 캘리브레이션 세트에 대해 단 한 번만 실행한다. 선택된 소수
전문가에 대한 입력/출력만 저장한다.

**Stage B: 전문가 단위 로컬 재생**
전체 모델을 GPU 메모리에서 해제한다. 한 번에 전문가 행렬(또는 전문가 블록)
하나만 로드한다. 저장된 전문가 입력으로 여러 후보 랭크를 평가한다.

메모리 요구량이 다음에서

```
전체 모델 + 모든 분해 + 모든 활성화
```

다음으로 바뀐다.

```
트레이싱 시점: 양자화된 모델 하나
이후: 전문가 하나 + 활성화 배치 하나 + 분해 하나
```

핵심 원칙: **전체 모델 실행은 트레이스 수집과 마지막의 제한적 검증에만
사용한다. 대부분의 랭크 스윕(sweep)은 전체 모델이 로드되지 않은 상태에서
수행한다.**

## 2. 권장 모델 규모

Toy0는 다음 조건을 만족하는 가장 작은 공개 MoE 모델로 시작해야 한다.

- 접근 가능한 Hugging Face 구현 존재
- 라우터 로짓(logits) 또는 라우팅 결정 노출
- 표준 SwiGLU 방식 전문가 사용
- 4비트 가중치 로딩 또는 CPU 오프로딩으로 RTX 3090 한 대에서 실행 가능

**실용적 권장 규모**

- 전체 파라미터 약 20억~80억
- 토큰당 활성 파라미터 약 5억~30억
- top-1 또는 top-2 라우팅
- 독립적으로 추출·재생 가능할 만큼 작은 전문가 행렬

RTX 3090 한 대에서 300억 파라미터급 MoE로 Toy0를 시작하지 않는다.

대형 MoE 모델은 소형 모델에서 가설이 이미 뒷받침된 이후에만 사용한다.

**모델 로딩 권장사항**

- 원본 라우팅 트레이스 패스에는 bitsandbytes NF4 또는 INT4 사용
- 가능하면 라우터 모듈과 선택된 전문가 모듈은 FP16/BF16 유지
- `device_map="auto"`는 필요할 때만 사용
- CPU 오프로딩은 트레이스 수집에만 사용, 전문가 로컬 재생에는 사용하지 않음
- 배치 크기 1
- 초기 시퀀스 길이 256 또는 512
- 캘리브레이션 forward pass 중 KV 캐시 비활성화

트레이싱에 사용하는 모델은 양자화되어도 무방하다(Toy0는 로드된 체크포인트
기준으로 랭크 근사를 비교하기 때문). 단, 추출된 대상 전문가는 분해와 로컬
재생 전에 FP16 또는 FP32로 변환해야 한다.

## 3. Toy0 범위

Toy0는 두 부분으로 나뉜다.

### Toy0-A: 단일 행렬 로컬 타당성 검증

**목표**: 하나의 전문가 내부에서 토큰별 필요 랭크가 다른지 확인한다.

**개입 대상**: `down_proj`만 저랭크 근사

**이유**: `down_proj`는 게이트된 중간 활성화 이후의 선형(linear) 연산이다.
이는 토큰 수준 출력 오차 계산을 쉽게 만들고, `gate_proj`/`up_proj`/
`down_proj`를 동시에 근사할 때 발생하는 비선형 오차의 복합을 피할 수 있다.

**최소 분석 단위**

```
2개 MoE 레이어 x 레이어당 자주 사용되는 전문가 2개 = 4개 (레이어, 전문가) 쌍
```

**권장**: 중간 레이어 1개 + 후반 레이어 1개, 각 레이어에서 라우팅 빈도가 높은
전문가 2개.

### Toy0-B: 전체 전문가 확인

Toy0-A가 성공한 경우에만 실행한다.

**개입 대상**: `gate_proj`, `up_proj`, `down_proj` 모두 근사

**목표**: 전문가 함수 전체를 근사할 때도 토큰별 랭크 이질성이 유지되는지 확인

Toy0-B는 처음에는 레이어 1개 x 전문가 1~2개만 사용한다.

Toy0-A, Toy0-B 어느 쪽도 예측기(predictor)를 학습하지 않는다.

## 4. 데이터셋 및 샘플 크기

소규모 일반 텍스트 캘리브레이션 세트를 사용한다.

**초기 권장 설정**

- 시퀀스 32개
- 시퀀스 길이 256
- 배치 크기 1
- 생성(generation) 없음, teacher-forced forward pass만 수행

선택된 전문가에 도달하는 토큰이 너무 적으면:

- 시퀀스를 64개로 늘리거나
- 시퀀스 길이를 512로 늘린다
- 두 가지를 동시에 늘리지 않는다

**선택된 (레이어, 전문가) 쌍당 목표 라우팅 토큰 수**

- 최소: 500개
- 권장: 1,000~3,000개
- Toy0 상한: 전문가당 약 5,000개

방법이 작동함을 확인하기 전까지는 더 많은 토큰이 필요하지 않다.

**데이터셋 분할**

- 트레이스/캘리브레이션 세트: 라우팅된 전문가 입력을 수집하고 분해를 생성하는 데 사용
- 평가 세트: 토큰별 랭크 오차를 평가하기 위한 별도 시퀀스

**권장 분할**: 캘리브레이션 50% / 평가 50%

활성화 인식(activation-aware) 분해를 구성하는 데 사용한 것과 동일한
활성화만으로 평가하지 않는다.

## 5. 라우팅 트레이스 수집

원본 모델을 실행하고 후보 MoE 레이어에만 훅(hook)을 등록한다.

**라우팅된 토큰마다 저장할 항목**

- sample_id
- token_position
- layer_id
- expert_id
- top-k 슬롯
- 라우터 확률 또는 라우터 점수
- 라우터 top-1/top-2 마진
- 전문가 입력 벡터
- down_proj 입력 벡터
- 원본 전문가 출력 벡터
- (여력이 되면) 잔차(residual) 은닉 벡터

Toy0-A에서 가장 중요한 텐서:

```
z_t : SwiGLU 활성화 이후 down_proj의 입력
y_t : 원본 down_proj 출력
```

왜냐하면:

```
y_t = W_down * z_t
```

**메모리 절약 규칙**

1. 선택된 (레이어, 전문가) 쌍만 저장
2. 캡처한 텐서는 즉시 CPU로 이동
3. 저장 활성화는 FP16으로 변환
4. 하나의 큰 파이썬 리스트가 아니라 청크 단위로 저장
5. attention 상태나 KV 캐시는 저장하지 않음
6. 모든 레이어의 전체 은닉 상태를 저장하지 않음
7. 목표 토큰 수에 도달하면 해당 전문가 수집을 중단

**권장 저장 형식**: (레이어, 전문가) 쌍당 파일 하나

```
traces/
    layer_08_expert_03_inputs.pt
    layer_08_expert_03_outputs.pt
    layer_08_expert_03_metadata.pt
```

CPU RAM이 제한적이면 NumPy memmap 또는 다중 샤드 파일을 사용한다.

## 6. 레이어와 전문가 선정

전체 활성화를 수집하기 전에, 비용이 낮은 라우팅 카운트 패스를 먼저 수행한다.

각 MoE 레이어와 전문가에 대해 카운트한다.

```
n(l,e) = 라우팅된 토큰 수
```

**선정**

- 중간 MoE 레이어 1개
- 후반 MoE 레이어 1개
- 각 레이어에서 가장 자주 사용되는 전문가 2개

**선정 기준**: `n(l,e) >= 500`

희귀 전문가는 Toy0에서 피한다. 샘플이 부족하면 랭크 분포 분석이 불안정해진다.

라우터 점수가 유난히 높거나 낮다는 이유만으로 전문가를 선택하지 않는다.
빈도가 주요 기준이어야 한다.

**선택 사항**: 강건성(robustness) 확인을 위해 이후 저빈도 전문가 하나를
추가로 포함할 수 있다.

## 7. 저랭크 분해

Toy0-A에서는 선택된 전문가의 `down_proj` 가중치만 분해한다.

```
W ∈ R^(d_out x d_in)
```

최대 랭크 분해 하나를 계산한다.

```
W = U * Σ * V^T
```

저장하는 것: `U`, `Σ`, `V`만.

랭크 r 실행은 prefix를 사용한다.

```
W_r * z = U[:, :r] @ (Σ[:r] * (V[:, :r]^T @ z))
```

랭크 64, 128, 256을 독립적으로 계산·저장하지 않는다.

이는 FERRET이 **하나의 중첩(nested) 분해**를 가정하기 때문에 필수적이다.

**정밀도 권장사항**

- 행렬이 CPU RAM에 들어가면 CPU에서 FP32로 SVD 계산
- 또는 GPU에서 한 번에 행렬 하나씩 `torch.linalg.svd` 사용
- 수치 오차가 허용 가능하면 재생(replay)을 위해 팩터를 FP16으로 변환
- 불안정성이 나타나면 특이값(singular value)은 FP32로 유지

전체 SVD가 너무 느리면:

- 무작위(randomized) SVD 사용
- 테스트할 최대 랭크만 요청
- 무작위 SVD 결과를 작은 부분집합으로 검증

예를 들어 테스트할 최대 랭크가 512라면 512개 성분만 계산한다.

## 8. 랭크 그리드

`{8, 16, 32, 64}`만으로 시작하지 않는다.

내재 차원(intrinsic dimension)이 큰 행렬에서는 이 랭크들이 너무 작아서
거의 모든 토큰이 가장 큰 후보 랭크를 필요로 하게 될 수 있다.

먼저 상대적으로 성긴(coarse) 그리드를 사용한다.

**권장 초기 그리드 (비율)**

```
{0.125, 0.25, 0.375, 0.5, 0.75, 1.0}
```

각 비율을 정수 랭크로 변환한다.

```
r = round(ratio * R_max)
```

랭크는 16 또는 32의 배수로 반올림한다.

예: `{128, 256, 384, 512, 768, 1024}` (정확한 값은 행렬 차원에 따라 다름)

첫 실행 후:

- 오라클 랭크가 집중되는 구간을 식별
- 해당 구간 내부에 랭크를 추가

정제된 그리드 예: `{256, 320, 384, 448, 512}`

최대 후보 랭크가 전체 행렬 랭크와 같을 필요는 없다. 다만 평가 구현이
올바른지 검증하기 위해 정확한 full-rank(또는 원본 출력) 참조값을 포함해야
한다.

## 9. 주요 오차 지표

토큰 t와 후보 랭크 r에 대해:

```
원본 출력:   y_t = W z_t
근사 출력:   y_hat(t,r) = W_r z_t
```

### 9.1 상대 L2 출력 오차

```
E_rel(t,r) = ||y_t - y_hat(t,r)||_2 / (||y_t||_2 + delta)
```

`delta = 1e-6` 사용. **Toy0-A의 주요 지표.**

### 9.2 코사인 오차

```
E_cos(t,r) = 1 - cosine(y_t, y_hat(t,r))
```

보조 지표로 사용.

### 9.3 라우터 가중 오차

전문가 기여도에 라우터 가중치 `g_t`가 곱해지는 경우:

```
E_weighted(t,r) = g_t * ||y_t - y_hat(t,r)||_2 / (||h_t||_2 + delta)
```

여기서 `h_t`는 잔차 또는 MoE 레이어 출력 스케일이다.

잔차 은닉 벡터가 저장된 경우에만 이 지표를 사용한다.

상대 전문가-출력 지표와 라우터 가중 지표 모두 보고해야 한다. 라우터
가중치가 낮은 토큰은 레이어 출력에 큰 영향을 주지 않으면서도 더 큰 전문가
출력 오차를 허용할 수 있다.

## 10. Oracle Rank 정의

각 토큰에 대해:

```
r_star(t; epsilon) = E_rel(t,r) <= epsilon 를 만족하는 가장 작은 r
```

여러 임계값을 평가한다.

```
epsilon ∈ {0.01, 0.02, 0.05, 0.10}
```

**권장 주요 임계값**: `epsilon = 0.05`

오차 범위를 확인하기 전에 하나의 임계값을 고정하지 않는다.

어떤 후보 랭크도 임계값을 만족하지 못하면:

```
oracle_rank = FAIL
```

암묵적으로 최대 후보 랭크를 할당하지 않는다.

**보고 항목**: FAIL 비율, 오라클 랭크 히스토그램, 중앙값, 평균, 25/75
백분위수.

거의 모든 토큰이 동일한 랭크를 받거나, FAIL이거나, 최대 후보 랭크를 받는
전문가는 FERRET에 유용하지 않다.

## 11. 필수 이질성(Heterogeneity) 분석

핵심 지표는 전역적인 랭크 변동이 아니다.

핵심 지표는 **레이어와 전문가를 모두 고정한 후의 오라클 랭크 변동**이다.

모든 (레이어, 전문가) 쌍에 대해 보고:

- 오라클 랭크 히스토그램
- 지배적(dominant) 랭크의 비중
- 유의미한 질량을 가진 랭크 구간(bin) 수
- 랭크 엔트로피
- 사분위 범위(IQR)
- 저랭크 토큰 비율
- 고랭크 토큰 비율
- FAIL 비율

**유의미한 이질성의 최소 증거**

- 지배적 랭크 비중이 80% 미만
- 최소 3개 랭크 구간에 의미 있는 질량 존재
- 최소 2개 랭크 구간이 각각 토큰의 10% 이상을 포함

정확한 임계값은 휴리스틱이지만, 결과가 한두 개의 이상치 토큰에 좌우되어서는
안 된다.

## 12. 동일 예산(Equal-Budget) 베이스라인

Toy0는 토큰별 오라클 할당을 강력한 정적 베이스라인들과 비교해야 한다.

### 12.1 전역 정적 랭크

선택된 모든 전문가에서 라우팅된 모든 토큰이 동일한 랭크를 받는다.

### 12.2 레이어별 정적 랭크

레이어 내 모든 토큰이 하나의 고정 랭크를 받는다.

### 12.3 전문가별 정적 랭크

전문가 e로 라우팅된 모든 토큰이 하나의 고정 랭크 `r(l,e)`를 받는다.

**가장 중요한 정적 베이스라인이다.** FERRET은 토큰별 할당이 이 전문가별
정적 정책보다 개선될 때만 의미가 있다.

### 12.4 무작위 동일 예산 혼합

예를 들어 오라클 평균 랭크가 320이고 사용 가능한 랭크가 256과 384라면,
다음과 같이 무작위로 랭크를 할당한다.

```
50% -> 256
50% -> 384
```

평균 랭크: `0.5*256 + 0.5*384 = 320`

최소 10개의 무작위 시드로 반복한다.

이는 단순히 두 랭크 수준을 섞는 것만으로 생기는 개선 효과를 통제하기
위함이다.

### 12.5 Oracle 토큰별 랭크

각 토큰이 자신에게 허용 가능한 최소 랭크를 받는다.

**모든 정책에 대해 보고**: 평균 실행 랭크, 평균/중앙값 상대 오차, p90/p95
상대 오차, 임계값 위반율, 이론적 저랭크 FLOPs.

## 13. 동일 연산량(Equal-Compute) 비교

저랭크 선형 레이어의 경우:

```
W_r z = U_r (Σ_r (V_r^T z))
```

이론적 곱셈-덧셈 비용은 대략:

```
r * d_in + d_out * r
```

행렬 차원이 동일하면 평균 랭크가 1차 근사 연산량 지표로 충분하다.

**주요 비교**: Oracle 토큰별 정책 vs 최선의 전문가별 정적 정책 (동일하거나
더 낮은 평균 랭크 조건)

**권장 지표**

```
상대 오차 감소율 = (Error_static - Error_oracle) / Error_static
```

**Toy0 성공 기준(제안)**

- 평균 오차 상대 감소 10% 이상, 또는
- 임계값 위반율 상대 감소 20% 이상

95% 부트스트랩 신뢰구간이 0을 넘어야 한다.

같은 시퀀스에서 나온 토큰들이 상관되어 있다면 시퀀스 수준 부트스트랩을
사용한다.

## 14. 단일 GPU 실행 절차

### Phase 1: 저비용 라우팅 카운트

1. 모델을 4비트로 로드
2. 배치 크기 1 사용
3. 짧은 시퀀스 16~32개 실행
4. 레이어·전문가별 라우팅 토큰 수 카운트
5. 레이어 2개, 전문가 4개 선정
6. 모델 삭제 또는 미사용 훅 해제

**예상 GPU 메모리**: 모델 크기에 따라 다르지만, 충분히 작은 MoE 모델과
4비트 로딩을 사용하면 24GB 이내여야 한다.

### Phase 2: 트레이스 수집

1. 동일 모델 재로드
2. 선택된 레이어에만 훅 등록
3. 선택된 전문가 활성화만 저장
4. 전문가당 1,000~3,000 토큰 확보 후 중단
5. 트레이스를 CPU 저장소에 증분 기록
6. 모델을 GPU에서 삭제
7. `torch.cuda.empty_cache()` 실행

### Phase 3: 전문가 추출

1. 가능하면 체크포인트를 CPU에서 로드
2. 선택된 전문가의 `down_proj` 가중치 추출
3. 행렬을 FP32로 변환
4. 절단(truncated) SVD 계산
5. 팩터를 디스크에 저장
6. 전문가를 순차적으로 처리

어떤 시점에도 모든 전문가의 팩터를 동시에 GPU에 올리지 않는다.

### Phase 4: 로컬 랭크 스윕

(레이어, 전문가) 쌍 하나에 대해:

1. 저장된 활성화 로드
2. SVD 팩터 로드
3. 활성화 청크 하나를 GPU로 이동
4. 원본 출력과 랭크-prefix 출력 계산
5. 오차 통계를 CPU로 이동
6. 청크에 대해 반복
7. 다음 전문가로 넘어가기 전 텐서 삭제

**권장 활성화 청크 크기**: 64~512 토큰 (행렬 차원과 메모리 사용량에 따라
조정)

### Phase 5: 정적-동적 분석

1. 각 임계값에 대해 오라클 랭크 생성
2. 전문가별 정적 베이스라인 계산
3. 동일 예산 무작위 혼합 구성
4. 품질-연산량 곡선 플롯
5. 부트스트랩 신뢰구간 계산
6. Go / No-Go 결정

### Phase 6: 제한적 전체 모델 검증

로컬 결과가 긍정적일 때만 실행한다.

1. 레이어 1개, 전문가 1개 선정
2. 해당 전문가에 대해서만 랭크 치환 구현
3. 평가: 원본 / 전문가-정적 / 오라클-토큰별 / 무작위 동일예산
4. 평가 시퀀스 16~32개 사용
5. 측정: ΔNLL, 로짓 KL divergence, top-1 토큰 일치율

Toy0 동안 모든 레이어의 모든 전문가를 교체하지 않는다.

## 19. Go / No-Go 기준

### Gate 1: 저랭크 타당성

선정된 전문가 4개 중 3개 이상이 유용한 중간 랭크 동작점을 달성하면 통과.

**제안 조건**: 랭크가 테스트된 최대 랭크의 50% 이하, 중앙값 상대 오차 5%
미만, p90 상대 오차 10% 미만.

### Gate 2: 전문가 내부 이질성

전문가 4개 중 3개 이상이 유의미한 오라클 랭크 변동을 보이면 통과.

**제안 조건**: 지배적 랭크 비중 80% 미만, 최소 3개 랭크 구간 점유, 최소
2개 구간이 각각 토큰의 10% 이상 포함.

### Gate 3: Oracle 우위

동일 평균 랭크 조건에서 오라클 토큰별 할당이 최선의 전문가별 정적 할당을
능가하면 통과.

**제안 조건**: 평균 오차 상대 감소 10% 이상 또는 임계값 위반율 상대 감소
20% 이상, 부트스트랩 95% 신뢰구간이 0을 배제.

### Gate 4: 제한적 모델 수준 확인

레이어 1개 개입에서 다음을 보이면 통과.

```
ΔNLL_oracle < ΔNLL_expert_static   (동일 평균 랭크 조건)
```

Gate 3이 실패하면 랭크 예측기를 학습하지 않는다.

Gate 1이 실패했지만 가중치 SVD를 사용했다면, 가설을 포기하기 전에
활성화 인식(activation-aware) 분해로 한 번 더 시도한다.

Gate 2가 실패하면, 해당 모델은 전문가별 정적 압축은 지원할 수 있지만
FERRET 방식의 토큰별 랭크 적응은 지원하지 않을 수 있다.

가장 작은 실행 가능 구성:

- **모델**: 24GB VRAM에서 4비트로 들어가는 가장 작은 호환 오픈 MoE 모델

## 22. 최종 방법론 요약

단일 RTX 3090에서 FERRET Toy0는 엔드투엔드 동적 MoE 시스템이 아니라
**오프라인 전문가 재생(replay) 실험**으로 구현되어야 한다.

원본 모델은 소수의 라우팅된 전문가 활성화를 수집하는 데만 사용된다. 이후
전체 모델은 GPU 메모리에서 제거되고, 선택된 전문가 하나씩 분해하여
평가한다.

**결정적 질문**

> 레이어와 전문가를 모두 고정한 상태에서, 토큰별 오라클 랭크 할당이 동일한
> 평균 실행 랭크 조건에서 최선의 전문가별 정적 랭크 할당보다 낮은 근사
> 오차를 달성하는가?

긍정적인 답은 더 큰 규모의 오라클 생성과 예측기 개발을 정당화한다.

부정적인 답은 전문가별 정적 압축으로 충분할 가능성이 높으며, 상당히 다른
분해 방식이나 오차 기준 없이는 FERRET의 토큰 적응형 랭크 가설을 추구하지
않아야 함을 의미한다.
