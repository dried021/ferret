## GPU 안전 정책 (2026-07-23 반영)

이 호스트(4x3090)는 다른 사용자와 공유한다. `scripts/00_config.py`는
`CUDA_VISIBLE_DEVICES`를 고정값으로 두지 않고, **매 실행 시작 시**
`nvidia-smi` + `ps`로 각 GPU의 compute process 소유자를 확인해서 **현재
사용자가 아닌 프로세스가 하나라도 있는 GPU는 통째로 제외**한다 (그 GPU에 여유
메모리가 있어 보여도 마찬가지). 안전하게 남는 GPU가 하나도 없으면 실행을 거부한다.

이 정책은 하드코딩된 `cuda_visible_devices` 값이 다른 사용자의 실행 중인 작업에
실제로 손을 댈 뻔했던 사건(2026-07-23) 이후 추가됐다. 이후 세션에서 dongjin이
작업을 GPU0→GPU1로 옮겼을 때도, 재실행 시 자동으로 감지해서 GPU0/2만 사용했다
(하드코딩 없이 매번 재확인됨) — 실제로 검증된 동작이다.

`configs/device_map.json`의 `max_memory`는 안전 검사를 통과한 GPU 부분집합에만
적용된다 (몇 번 GPU인지는 실행마다 다를 수 있음).

**`otter/scripts/safe_gpus.sh`** (Phase 0 이후 D2MoE 실행용, bash 버전)는
사용자 요청(2026-07-24)으로 `MAX_GPUS=2` 하드 캡도 추가됐다 — 다른 사용자
프로세스가 없는 GPU가 3~4장이어도, 항상 인덱스가 낮은 2장까지만 쓴다. Phase 1
실행 중 dongjin/kahyeon이 여러 번 다른 GPU로 작업을 옮겼는데, 그때마다
자동으로 재감지해서 항상 "다른 사람이 안 쓰는 GPU 중 최대 2장"을 골랐다.

**저장소:** [github.com/lliai/D2MoE](https://github.com/lliai/D2MoE) (Apache-2.0).
`otter/D2MoE/`에 clone 완료 (22MB, `.gitignore`에 `otter/D2MoE/`

아직 `pip install`은 안 함 — 아래 이유로 실행 전 결정이 필요하다.

### 발견 1 — 모델별 스크립트가 완전히 분리되어 있고, 각각 기본 체크포인트가 다르다

`README.md`와 코드에서 확인한 실제 기본값:

| 스크립트 | `--base_model_path` 기본값 | 비고 |
|---|---|---|
| `D2-mixtral.py` | (직접 지정) | bf16 90GB+ |
| `D2-deepseek.py` | `deepseek-ai/deepseek-moe-16b-base` | bf16 ~31GB, **4x3090(96GB)에서 유일하게 현실적** |
| `D2-Phi.py` | Phi-3.5-MoE | 미확인 (아직 안 읽음) |
| `D2-qwen.py` | **`Qwen/Qwen2-57B-A14B`** | bf16 114GB+ — 우리 호스트에서도 안 돌아감 |

즉 "Qwen 지원"이라고 해도 그 대상은 **Qwen2-57B-A14B**지, 우리가 Toy0/Phase 0.5/
0번에서 쓴 **Qwen3-30B-A3B가 아니다.**

### 발견 2 — `D2-qwen.py` 경로는 Qwen3-30B-A3B와 아키텍처가 다르다 (어댑터로 안 됨)

`model/merge_qwen.py`가 `from transformers.models.qwen2_moe.modeling_qwen2_moe import *`를
직접 import하고, expert들을 `nn.ModuleList([meanW_deltaUV(...) for _ in range(num_experts)])`
형태로 **expert마다 개별 서브모듈**로 다룬다. 반면 우리 Qwen3-30B-A3B는 (moe_hooks.py에서
이미 검증했듯) `Qwen3MoeExperts`가 `gate_up_proj`/`down_proj`를 **expert 차원까지 포함한
배치 3D 텐서 하나**로 갖는 구조다 (개별 `nn.Linear` submodule이 아예 없음). 이건 설정값
몇 개 바꿔서 될 문제가 아니라 `merge_qwen.py`에 준하는 새 병합/분해 모듈을 처음부터
작성해야 하는 수준의 포팅 작업이다 — Qwen3 지원은 **가볍지 않다.**

`D2-deepseek.py` 경로는 사정이 다르다: `model/modeling_deepseek.py`가 HuggingFace
`transformers`의 DeepSeek 구현에 기대지 않고 **자체 vendored 모델 코드**를 갖고
있어서, 특정 `transformers` 버전에 대한 의존이 상대적으로 약하다.

### 발견 3 — `requirements.txt`가 우리 환경과 정면으로 충돌한다

D2MoE repo pin: `torch==2.3.1`, `transformers==4.42.4` (+ `deepspeed==0.13.3`,
`tensorrt-cu12-bindings==10.5.0` 등 무거운 의존성 다수).
우리 `torch_env`(environment.txt): `torch 2.5.1+cu121`, `transformers 5.13.1`.

`transformers==4.42.4`는 Qwen3 아키텍처 지원 이전 버전이라 **Qwen3-30B-A3B는 그
환경에서 애초에 로드도 안 된다** (발견 2와 별개로, 환경만으로도 막힌다). 그리고
이 `requirements.txt`를 지금 `torch_env`에 그대로 설치하면 Toy0/Phase 0.5/0번이
의존하는 torch 2.5.1/transformers 5.13.1 조합이 깨진다.

**결정: D2MoE 전용 conda 환경을 새로 만든다 (`torch_env`를 건드리지 않음).**
이름 후보: `d2moe_env`. `torch_env`는 계속 Qwen3-30B-A3B probe 전용으로 유지한다.

### 발견 4 — 이 호스트 디스크가 매우 빠듯하다 (설치 전 반드시 확인할 것)

```
/ (root, /home 포함):   1.9T 중 1.8T 사용, 40G 여유 (98%)  <- conda env가 여기 있음
/mnt/HDD (HF_HOME):     7.3T 중 4.9T 사용, 2.0T 여유 (72%) <- 모델 체크포인트는 여기로
```

`torch_env`가 6.0GB인 것을 감안하면, D2MoE의 `requirements.txt`(deepspeed +
tensorrt 포함) + `flash-attn` 컴파일까지 새 env를 만들면 **비슷하거나 더 큰
용량(대략 6~10GB)**이 root 디스크(40GB 남음, 여러 사용자 공유)에서 소모된다.
DeepSeek-MoE-16B 체크포인트(~31GB, bf16)는 `HF_HOME=/mnt/HDD/...`로 받으므로
root가 아니라 `/mnt/HDD`(2.0TB 여유)를 쓴다 — 이건 안전.

### 설치 완료 (2026-07-24)

```bash
conda create -n d2moe_env python=3.10 -y
cd otter/D2MoE
conda run -n d2moe_env pip install -r requirements.txt      # 성공, 에러 없음
cd lm-evaluation-harness && conda run -n d2moe_env pip install -e .   # 성공
```

`d2moe_env`는 `torch_env`와 완전히 분리된 별도 conda 환경이고, 설치 후
`torch_env`가 여전히 정상 동작하는 것을 확인했다 (Qwen3 파이프라인 무관).
`d2moe_env`에서 `torch.cuda.is_available()` True, `device count: 4` 확인.

**flash-attn은 설치하지 않기로 함.** `pip install flash-attn==2.5.9.post1`이
`OSError: CUDA_HOME environment variable is not set`로 실패했다 — 이 호스트에
nvcc/CUDA 툴킷이 시스템 전역으로 설치돼 있지 않다 (`nvidia-smi`가 보여주는 건
드라이버가 지원하는 최대 CUDA 버전이지, 컴파일용 툴킷이 아니다). CUDA 툴킷을
새로 설치하는 대신 코드를 읽어 확인한 결과, `model/modeling_deepseek.py`는
`DeepseekAttention`(eager) / `DeepseekSdpaAttention` / `DeepseekFlashAttention2`
세 가지 attention 구현을 `config._attn_implementation`으로 선택하게 되어 있고,
flash_attn import는 `if is_flash_attn_2_available():`로 조건부라 **flash-attn
없이도 정상 동작한다** (transformers가 자동으로 sdpa로 폴백). 압축 알고리즘
자체(Fisher merge, SVD, pruning)는 attention 구현과 무관하므로 이 선택이
재현 결과에 영향을 주지 않는다 — 단지 속도/메모리 특성만 약간 달라진다.

**최종 디스크:** 89GB → 78GB 여유 (`requirements.txt` 설치로 ~11GB 사용, 예상
범위 안). `/mnt/HDD`는 아직 그대로 (모델 체크포인트 다운로드는 다음 단계).

### GPU 안전 검사를 D2MoE 실행에도 적용

D2MoE 원본 스크립트에는 `00_config.py`의 GPU 소유권 안전 검사가 없다.
`otter/scripts/safe_gpus.sh`를 만들어 `_safe_gpu_indices()`와 동일한 로직(다른
사용자 프로세스가 있는 GPU는 통째로 제외)을 bash에서 `source`해서 D2MoE 실행
커맨드 앞에 매번 적용한다 (`CUDA_VISIBLE_DEVICES=$SAFE_GPUS python ...`).
실전에서 이미 두 번 작동을 확인했다 — dongjin이 GPU를 옮겼을 때, 그리고 이번
세션 중 kahyeon(`cdpruner` env)이 GPU2에서 새 작업을 시작했을 때 모두 자동으로
감지해서 제외했다.

### Step 1 완료 — expert routing frequency (2026-07-24)

`deepseek-ai/deepseek-moe-16b-base` 다운로드 완료 (~31GB, `/mnt/HDD`).

```bash
python preprocess/get_expert_freq.py --base_model_path=deepseek-ai/deepseek-moe-16b-base \
    --save_path=... --model_type=deepseek --dataset_name=wikitext --split=train \
    --seed=42 --max_samples=20000 --batch_size=4
```

**두 가지 실행 전 이슈를 고쳐야 했다:**
- **flash_attn 정적 import 검사 오탐.** 체크포인트 자체의 `trust_remote_code` 모델
  파일(우리가 고친 vendored 사본과 별개로, HF Hub에서 받은 것 자체)도
  `if is_flash_attn_2_available(): from flash_attn import ...`로 조건부 import를
  쓰는데, `transformers.dynamic_module_utils.check_imports()`가 파일 텍스트를
  정적으로 스캔해서 **조건문 안에 있어도** import 대상을 못 찾으면 무조건
  에러를 낸다 (`try/except`만 예외로 봐줌). 다운로드된 체크포인트의
  `modeling_deepseek.py`를 `if` → `try/except ImportError`로 바꿔서 해결 —
  실제 로직은 그대로(둘 다 flash_attn 없으면 그냥 건너뜀), 정적 분석만 통과시키는
  패치. (처음 시도에서 주석에 실수로 "except"라는 단어를 넣었다가 정규식이 엉뚱한
  지점에서 끊겨서 재실패했었다 — `transformers`의 `get_imports()`가
  `try...except` **텍스트 블록 전체**를 정규식으로 걷어내는 방식이라, 주석에
  들어간 낱말도 매치에 영향을 준다.)
- **`device_map="auto"`가 GPU 한 장에 가중치를 몰아넣어서 OOM.** `--batch_size=4`로
  낮춰서 해결 (기본값 16은 이 호스트 GPU 한 장 기준 로짓 계산에서 OOM).

**결과:** `deepseek_wikitext_20000_expert_frequencies.json` 저장, 총 소요 ~51분
(forward-only, 20000 샘플).

### Step 2 — 진짜 gradient Fisher 계산 시도, 반복 OOM (2026-07-24)

`preprocess/get_fisher.py`(기본 설정: `num_samples=1024`, `seqlen=2048`, 전체
파라미터 `requires_grad=True`, element-wise Fisher를 GPU에 계속 누적)를 그대로
돌리자 **첫 샘플의 backward()에서부터 OOM.** 원인을 좁히려고 순서대로 시도:

1. 기본 `device_map="auto"` → GPU 한 장에 22.5GB 가중치가 몰려서 OOM
2. Fisher 누적값을 CPU로 옮기는 패치 → 효과 없음 (누적값이 아니라 backward
   자체가 이미 OOM 지점)
3. GPU 3장에 10GiB씩 균등 분배 + CPU offload 허용 → 여전히 OOM (offload된
   파라미터의 backward가 메모리를 안전하게 못 풂 — accelerate의 큰 모델
   offload hook은 추론용으로 설계된 것이라 학습(backward)에서 신뢰하기 어려움)
4. `seqlen` 2048→1024 → 거의 동일한 지점에서 OOM (활성화 메모리가 병목이
   아니었다는 뜻 — 진짜 병목은 **모든 파라미터의 gradient가 그 파라미터와 같은
   GPU에서 가중치와 동시에 존재**해야 한다는 것: 16B 모델 전체에 대해 backward
   한 번을 걸면 가중치(~31GB) + gradient(~31GB)가 동시에 필요한데, 이건
   GPU 3장(70.7GB)에도 빠듯하고 2장(47GB)에는 원천적으로 안 맞는다)

이 시점에 사용자가 "GPU 2장만 써서 되게 하라"는 요구와 함께, **전체 모델이 아니라
레이어 하나의 expert만 gradient를 켜고, element-wise가 아니라 expert-scalar로
Fisher를 누적하라**는 구체적 설계를 제시했다 — 이게 실제 해결책이었다
(아래 Fisher Pilot A).

### Fisher Pilot A — 진짜 해결책 + 첫 실제 검증 결과 (2026-07-24)

**설계 변경 (사용자 지침):**
- 레이어 전체가 아니라 **레이어 1개씩** 처리, 그 레이어의 expert 파라미터만
  `requires_grad=True` (나머지 전부 `False`) → gradient 메모리가 ~31GB에서
  ~1-2GB(그 레이어의 expert 수만큼)로 줄어듦
- element-wise Fisher(파라미터와 같은 크기)를 저장하지 않고, **expert별 scalar
  하나**(`sum(grad^2)`)만 누적 — 우리가 검증하려는 건 "언어에 따라 어떤 expert가
  중요한지 순위가 바뀌는가"이지 실제 압축에 쓸 element-wise 통계가 아니므로 이걸로
  충분
- 짧은 시퀀스(seqlen 192, 논문 기본 2048 대비 훨씬 작음), batch size 1,
  조건당 token budget 768(512~1024 권장 범위), seed 1개, `model.zero_grad(set_to_none=True)`
  매 샘플마다, optimizer 없음
- 압축 실행에 필요한 element-wise Fisher와, 이 가설 검증용 expert-scalar Fisher를
  **별개로 취급** — 후자 하나 검증하겠다고 전자와 같은 비용을 치르지 않는다

**레이어 선택:** DeepSeek-MoE-16B는 실제로 28개 레이어(0번은 dense, 1~27이 MoE)라
Qwen3(48개 레이어)에서 쓰던 8/22/38 같은 번호가 그대로 적용되지 않는다. 상대
깊이를 맞춰 early=4(~14%) / transition=16(~61%) / sensitive=24(~86%) / final=27(100%,
진짜 마지막 레이어)로 선정.

**구현:** `otter/scripts/fisher_pilot_a.py`. 진짜 Fisher는 모델의 원래 forward를
그대로 쓰고 target 레이어 expert의 `.grad`만 읽는다 (몽키패치 불필요). Proxy는
`DeepseekMoE.forward`의 학습모드 분기를 그대로 복사해서 캡처 로직만 추가한
버전으로 대상 레이어의 forward만 바꿔치기 (Toy0/Phase 0.5가 Qwen3에 썼던 것과

**`otter/scripts/phase1_merge_eval.py`** — `D2-deepseek.py`가 쓰는
`Merge_deepseekMoE(...).merge_experts(...)`를 cfg/control_name/LLMPruner
프레임워크 없이 직접 호출. 이 과정에서 D2MoE 자체의 실제 버그/설계와 부딪힌
문제들:
- `model/merge_deepseek.py`가 `from hf.utils import ...`(절대 import)를 써서

- `HiddenRepresentationPruning.__init__`이 `cfg['prune_metric']` 등, 원래는

  거대한 범용 pruning 프레임워크 설정 함수)이 채워주는 top-level cfg 키를
  요구 — 필요한 키만 직접 채워서 그 프레임워크 전체를 우회
- `meanW_deltaUV.forward()`의 `self.layer_order not in cfg['skip_layers']`
  분기가 pp_ratio/probe 기반 pruning 경로로 빠지는데, `Merge_deepseekMoE.__init__`이
  **`layer_order`를 애초에 안 넘겨서** 모든 expert의 `self.layer_order`가
  파라미터 기본값 `[]`임 (repo 버그) → `cfg['skip_layers'] = [[]]`로 맞춰서
  단순 mean+delta 경로(우리가 원하는 경로)를 타게 함
- **`DELTA_RATIO=0`은 이 코드베이스에서 구조적으로 미지원.** `delta_ratio==0`이면
  `__init__`이 `delta_u1~delta_v3` 모듈 자체를 안 만드는데 `forward()`는
  무조건 참조 — repo가 애초에 `delta_ratio=0` 케이스를 고려하지 않음. 대신
  **`svd_scale=None`으로 `DELTA_RATIO=0.8`(논문 예제값 그대로)을 쓰는 방법을
  찾음** — `merge_experts()`의 `delta_share_V=False, delta_share_U=False`
  분기에 `if svd_scale is not None: (whitened SVD) else: (plain SVD)` 폴백이
  이미 있어서, get_scale.py 없이도 "Fisher-merge 기반 + (whitening 없는) SVD
  delta"라는, 논문과 압축률은 같고 activation-aware 향상 기법만 빠진 결과를
  얻을 수 있었다.
- 레이어 27개를 순회하며 매번 이전 레이어의 원본(64-expert, ~1.1GB) `mlp`를
  교체하는데 명시적으로 안 지워주면 GPU 메모리가 27번 누적돼 OOM — `del` +
  `gc.collect()` + `torch.cuda.empty_cache()`를 레이어마다 추가

### 0) bits-per-byte 재계산 — 완료, 중대한 발견 (2026-07-24)

사용자가 baseline KO PPL(3.87)이 EN(19.93)/ZH(22.97) 옆에서 지나치게 낮다고
지적 — 언어 난이도로는 설명 안 되는 수준이라며 tokenizer 정규화 문제를
의심했다. `bpb_recompute.json`을 만들어 이미 저장된 `eval_ppl.json`의
`n_tokens`만으로 (모델 재실행 없이) bits-per-byte를 역산해본 결과, **의심이
정확히 맞았다**:

```
tokenizer 직접 확인 (deepseek-moe-16b-base):
  "안녕하세요, 오늘 날씨가 좋습니다." -> 34 tokens (한글 음절이 UTF-8 byte-fallback으로
      쪼개짐, 디코드하면 대부분 잘못된 단독 바이트 '�')
  "Hello, the weather is nice today." -> 9 tokens (거의 단어 단위)
  "你好,今天天气很好。" -> 7 tokens ("你好"가 통째로 토큰 하나)
```

같은 FLORES 60문장 기준 baseline n_tokens: EN 1834, **KO 7174**, ZH 1944 —
같은 내용(병렬 번역)인데 한국어만 토큰 수가 약 3.9배. per-token PPL은 토큰

작아지므로) 기계적으로 낮아진다 — Korean PPL 3.87이 낮은 건 압축이 한국어를

때문**이다.

### 1) 예산 정상화 + seed 3개 — 완료 (2026-07-24 시작, 2026-07-25 05:39 완료)

**사전 등록 (실행 전, 결과 확인 전 기록):**

- calibration 예산을 16 samples/seqlen 256(1차 pilot)에서 **64 samples/seqlen
  512**로 올린다 (`phase1_fisher.py`의 원 논문 방향 최소선). get_expert_freq
  step은 이미 max_samples=2000으로 pilot 때부터 이 축소 예산과 무관하게
  더 컸다.
- seed 0/1/2, 총 3 seed × 4조건(baseline 제외) = 12 run.
- 이번 재실행과 동시에 **calibration-평가 문장 중복 제거**도 반영한다
  (`phase1_calib_data.py`가 이제 평가용 앞 60문장을 calibration pool에서
  명시적으로 제외).
- **가설-확정 기준 (H2, own-language 이득):** 언어 L(EN/KO/ZH) 각각에 대해
  "own-language 이득" = (L이 calibration에 없는 다른 두 단일-언어 조건의 bpb
  증가율 평균) − (L 자신의 calibration 조건에서의 bpb 증가율). 이 값이
  양수면 "자기 언어 calibration이 그 언어를 더 잘 보존한다"는 뜻(H2 방향).
  - **주 기준:** 3언어 모두에서 own-language 이득의 3-seed 평균이 양수이고,
    3-seed 부트스트랩 95% CI가 0을 배제하면 **H2 유지**.
  - **보조 기준 (seed 3개뿐이라 부트스트랩 CI가 거칠다는 걸 알고 추가):**
    3언어 모두에서 own-language 이득이 **3개 seed 전부 개별적으로 양수**이면
    이것만으로도 방향성 증거로 인정한다 (부트스트랩 CI가 넓게 나와도).
  - 언어 3개 중 1~2개만 기준을 만족하면 "부분 지지", 전부 만족 안 하면
    "H2 기각" — 결과를 보기 전에 이 세 등급을 그대로 쓴다.
  - 판정 스크립트: `scripts/phase1_seed_gate.py` (실행 전 작성, 결과 파일이
    생기는 대로 그대로 돌림 — 사후에 기준을 바꾸지 않기 위해).
- **예상 소요 시간:** 실측 기반 추정 (16×256 pilot의 실제 레이어별 로그,
  `logs/phase1_fisher_english_only.log`, 평균 ~30s/layer에서 역산) — 64×512에서
  Fisher 단계만 조건당 ~1.6시간, freq(~3분)+merge/eval(~19분) 포함하면 조건당
  ~2시간, 12 run(4조건×3seed) 총 **~23~24시간**. GPU는 계속 2장만 쓴다
  (`MAX_GPUS=2`). 128×2048(사용자가 "가능하면"으로 언급한 상한)은 같은 방식
  추정 시 조건당 Fisher만 ~3시간대로 늘어나 총 40시간 이상(약 2일) — 이번엔
  일단 64×512로 진행하고, 결과를 본 뒤 그 이상 예산이 필요한지 다시 판단한다.
- 실행: `scripts/run_phase1_seeds.sh` (baseline 1회 + seed×조건 12회 순차 실행,
  매 커맨드 전 `safe_gpus.sh` 재확인).

**실행 중 발생한 일:** seed0 4조건 완료 직후(약 4.25시간, 조건당 실측 ~64분 —
사전 추정 ~2시간/조건보다 훨씬 빨랐음) seed2/english_only 시작 시점에

추가, (b) `eval_ppl.json` 존재 여부로 이미 끝난 조건/seed를 건너뛰는 재개
가능한 형태로 고쳐서 seed2부터 재개 — 이후 seed1 나머지 3조건 + seed2 4조건
전부 에러 없이 완료됐다 (8/12 → 12/12).

**H2_HELD — 사전 등록한 주 기준(3언어 모두 3-seed 부트스트랩 95% CI가 0 배제)을
그대로 만족한다.** 세 언어 모두 own-language 이득이 양수이고 3개 seed 전부
개별적으로 양수다.

**단, 주장을 "H2 성립"으로 평평하게 쓰지 않는다 — 통계적 보편성과 실질적
크기를 분리해서 쓴다 (사용자 리뷰 반영, 2026-07-25).** KO의 절대 이득
(+5.60%p)이 EN(+0.75%p)·ZH(+0.71%p)보다 훨씬 크다는 것 자체는 "저하 폭이
큰 언어라 이득도 스케일상 커 보이는 것"일 수 있다는 규모 효과(scale effect)
가능성이 있어, 이를 배제하기 위해 **상대 비율**(own-language 이득 ÷ 자기
언어를 뺀 나머지 두 조건의 평균 저하폭)로 다시 계산했다:

```
eng_Latn: per-seed relative %=[4.77, 7.39, 2.32]  mean=4.83%
kor_Hang: per-seed relative %=[24.44, 24.20, 24.04]  mean=24.23%
zho_Hans: per-seed relative %=[7.33, 4.77, 2.83]  mean=4.98%
```

**절대·상대 두 척도 모두에서 KO가 EN/ZH의 약 5배** — 규모 효과로 설명되는
정도를 넘어선다. 따라서 결론은 층을 나눠 쓴다: **"own-language 이득은 세
언어 모두에서 통계적으로 존재한다(보편적)"이지만, "그 실질적 크기는 압축에
가장 취약한 언어(KO)에 집중된다"** — EN/ZH의 +0.7~0.75%p는 22~23%대
저하 옆에서는 배포 결정을 바꿀 만한 크기가 아니다. 이 비대칭은 이전에
논의한 "사전학습 데이터가 적어 취약한 언어일수록 calibration 민감도가 크다"는
프레임과 같은 방향이다 — 아래 "다음 단계" 저자원 언어 실험이 이 패턴을
KO 하나의 사례에서 일반화된 패턴으로 검증하는 자리다.

**범위 한정 — 이 결과는 "Fisher-merge 경로 단독"의 효과다.** `delta_ratio=0.8`
+ `svd_scale=None`(whitening 미적용) + pp_ratio 미적용이므로, "D²-MoE가
calibration 언어에 민감하다"라고 쓰면 안 되고 **"D²-MoE의 Fisher-merge 단계가
calibration 언어에 민감하다"**로 한정해서 쓴다. whitening을 켰을 때 이
효과가 증폭될지, 상쇄될지, whitening 경로가 지배할지는 아직 모른다 — 아래
2) 2×2 실험의 사전 등록 예측을 이번 수치로 구체화했다: "scale(whitening)
언어만 바꾸는 조건에서 own-language 이득이 KO 기준 +5.60%p보다 크면
whitening이 주범, 작으면 Fisher가 주범."

**결과표에서 추가로 보이는 패턴 (사전 등록 게이트 밖, 탐색적 관찰):** macro
기준으로는 **Balanced가 최선**(16.06, KO-only의 16.19와 거의 동률), non-EN
기준으로는 **KO-only가 최선**(15.97, Balanced의 16.22가 근소하게 2위) — 둘 다
EN-only/ZH-only(macro 17.0~17.2대)보다 뚜렷이 낫다. ZH-only calibration은 ZH
자신은 잘 보존하지만(13.47, 전체 최저) KO를 크게 희생시켜(23.29, 전체 최고)
전체적으로는 손해다. 1차 seed=1 pilot에서 봤던 "EN-only가 macro 최선"이라는
결과는 이번 3-seed 재현에서 사라졌다 — seed noise였던 것으로 보인다.

**부록감 관찰 — EN/ZH 교차 패턴:** ZH-only calibration이 EN 평가에서
EN-only calibration 자신보다 더 낫고(14.28 vs 14.72), EN-only calibration도
ZH 평가에서 준수하다(13.93, ZH-only의 13.47 다음으로 좋음). EN과 ZH가 서로를
어느 정도 대신할 수 있다는 뜻으로, 앞서 관찰한 "EN/ZH 덩어리" 패턴의 추가
근거다 — 저자원 언어 실험에서 이 덩어리 밖 언어들과 비교할 기준점이 된다.

### 1.5) placebo (noise floor) — 완료 (2026-07-25, 06:29 시작 → 12:31 완료, 6시간)

**왜 필요한가.** 1)의 own-language 이득 CI는 n=3 부트스트랩이라 통계적으로
약하고(조합이 10개뿐), 무엇보다 **noise floor 자체를 잰 적이 없다.**
Toy0/Phase0.5는 english_a/english_b(같은 언어, 다른 표본) placebo로 이걸
확보했는데 Phase 1엔 없었다. 기존 데이터로 대체 확인해보니(같은 조건 내
seed 변동폭) EN(0.90%p)과 ZH(0.68%p)는 own-language 이득(각각 0.75%p,
0.71%p)과 같은 크기 — **noise floor와 구분이 안 된다.** KO만 변동폭(0.17%p)이
이득(5.60%p)의 1/33 수준으로 확실히 작다. 이 대체 확인은 "같은 조건 자체의
변동"이라 own-language 이득(조건 간 차이, 분산이 두 조건 변동의 합성)과
통계량 구조가 다르다는 지적에 따라, 진짜 A-vs-B 비교로 다시 잰다.

**사전 등록 (실행 전, 결과 확인 전 기록):**

- **새 조건:** `english_only_b`, `korean_only_b` (arm B) — 각 3 seed, 총 6 run.
  `phase1_calib_data.py`가 언어별 post-eval-exclusion pool을 원본 FLORES
  인덱스 기준으로 반씩 나눠(`pool[:half]`=arm A, `pool[half:]`=arm B) arm B는
  그중 절반만 쓴다 — Toy0의 `token_budget_chunks` disjoint-chunk-carving과
  같은 아이디어를 pool 레벨에 적용. **한계 공개:** arm A(기존 3 seed, 이미
  완료)는 원래 전체 pool에서 뽑았으므로 arm B의 절반과 완전히 겹치지 않는다는
  보장은 사후적으로는 못 한다 — arm A를 다시 돌리지 않는 한 불가능. arm B
  pool 자체는 다른 어떤 조건도 손대지 않는 깨끗한 절반이다 (확인: EN/KO
  각각 pool 952문장을 476/476으로 분할, 두 절반 교집합 0개, 코드로 검증).
  ZH는 예산상 placebo 없음 — "판단 불가"로 남겨둔다.
- **calibration 예산:** 1)과 동일 (64 samples, seqlen 512, get_expert_freq는
  max_samples=2000).
- **해시 로그:** `phase1_fisher.py`가 이제 매 실행마다 calibration 텍스트의
  MD5 해시와 첫 샘플 미리보기를 로그에 남긴다 (Toy0와 동일한 관행).
- **noise floor 정의 (고정):** `noise_floor(언어) = max_{seed∈{0,1,2}}
  |bpb_increase(arm A, seed, 언어) − bpb_increase(arm B, seed, 언어)|` —
  평균이 아니라 최댓값(더 엄격한 = 통과하기 어려운 기준).
- **판정 기준 (고정, margin=2배):** `own-language 이득 > 2 × noise_floor`이면
  **SUPPORTED**, `0 < 이득 ≤ 2×floor`이면 **INCONCLUSIVE**, `이득 ≤ 0`이면
  **NOT_SUPPORTED**. 2배는 Toy0 게이트(1.5배)보다 엄격하게 잡았다 — placebo
  대비 비교라 반복성 확인보다 기준을 세게 잡아야 한다는 판단. 이 숫자는 실행
  전에 여기 기록하고 이후 바꾸지 않는다.
- **판정 스크립트:** `scripts/phase1_placebo_gate.py` (실행 전 작성).
- **실행:** `scripts/run_phase1_placebo.py` (재개 가능, `run_phase1_seeds.sh`와
  동일한 안전 패턴). 실측 소요 6 run, 총 6시간(예상 ~6.4시간과 거의 일치),
  에러 없이 완료.

**결과 (`scripts/phase1_placebo_gate.py` 그대로 실행, 사전 등록 기준 그대로 적용):**

```
eng_Latn: per-seed |A-B| diff=[0.434, 0.562, 0.058]  noise_floor(max)=0.562
          own_gain=0.745  threshold(2x floor)=1.124  -> INCONCLUSIVE
kor_Hang: per-seed |A-B| diff=[0.357, 0.261, 0.504]  noise_floor(max)=0.504
          own_gain=5.598  threshold(2x floor)=1.008  -> SUPPORTED
zho_Hans: NO_PLACEBO (chinese_only_b 없음)  own_gain=0.705
```

**KO는 진짜 placebo 검증을 통과했다.** noise floor(0.504%p)의 2배 기준
(1.008%p)을 own-language 이득(5.598%p)이 약 5.6배로 넘어선다 — 원값 대비로도
floor의 약 11배. 지금까지 나온 모든 확인(절대 크기, 상대 비율, 이제 진짜
placebo까지) 중 어느 것으로도 KO의 own-language 효과를 노이즈로 설명할 수
없다. **이게 이 프로젝트에서 가장 방어 가능한 단일 결과다.**

**EN은 placebo 기준으로 INCONCLUSIVE로 확정한다.** own_gain(0.745)이
noise floor(0.562) 자체보다는 크지만, 2배 margin(1.124)에는 못 미친다 —
"효과가 없다"(NOT_SUPPORTED, 이득 ≤ 0)는 아니고, "이 예산·이 margin으로는
noise와 확실히 구분되지 않는다"는 뜻. 더 큰 calibration 예산이나 seed 수로
noise floor 자체를 좁히면 판정이 바뀔 수 있지만, 지금 결과로 EN의
own-language 효과를 주장하지 않는다.

**ZH는 여전히 판단 보류.** placebo를 안 돌렸으므로 own_gain(0.705, EN과
비슷한 크기)이 noise와 구분되는지 모른다 — EN과 비슷한 크기라는 점에서
EN처럼 INCONCLUSIVE일 가능성이 높다고 추정할 뿐, 확인된 사실은 아니다.

**결론 갱신 (핵심 발견 6번 대체):** "own-language 이득이 세 언어 모두
통계적으로 보편적이다"라는 이전 문장은 이제 폐기한다. 대신: **"KO의
own-language 이득은 placebo 대비로 확실히 검증됐고, EN은 미확정, ZH는
미검증이다."** H2는 KO 한 언어에서 강하게 지지되는 상태이지, 세 언어 모두에서
성립한다고 쓸 수 없다.

### 2) whitening 복원 (get_scale.py) → Fisher×Scale 2×2 — 자체 재구현으로 완료, 결과는 PRELIMINARY (2026-07-26)

사용자 지적: 지금 결과는 "Fisher merge 경로"만의 효과이고, 언어 효과가 가장
직접적으로 들어올 수 있는 **whitening(activation-aware SVD scale) 경로는
아직 켜본 적이 없다.**

**get_scale.py 메모리 누수 — 원인 규명 및 수정 완료 (버그 2개).** 코드를
직접 읽어서 첫 번째 버그를 찾았다: 레이어마다 hook으로 누적한
`process_subset[name].scaling_diag_matrix`(전문가별 [hidden,hidden] float32
GPU 텐서, 64 experts × 레이어당 ~2.5GB)를 다 쓴 뒤 지워야 하는데, 실제 코드는
`process_subset[name].raw_scaling_diag_matrix = None`이라는, **애초에 어디서도
설정된 적 없는 죽은 속성**을 지우고 있었다 — 진짜 누적 텐서
(`scaling_diag_matrix`, "raw_" 접두어 없음)는 한 번도 해제되지 않고
매 레이어가 끝난 뒤에도 해당 expert Linear 모듈에 영원히 살아남았다. 계산해보면
레이어 6개만 지나도 ~14.8GB가 누적되는데, 이게 정확히 "예산과 무관하게
~6/28 레이어에서 OOM"이라는 관찰된 증상과 일치한다. **1차 수정:**
`process_subset[name].scaling_diag_matrix = None` 추가.

1차 수정만 넣고 다시 돌려서 실시간으로 GPU 메모리를 모니터링했더니, 예전
OOM 지점(레이어 6개)은 훨씬 넘어섰지만 **메모리가 여전히 서서히 계속
증가했다** (34GB → 38GB → 42GB 근처까지, 결국 kill). 원인은 **두 번째,
별개의 누수**: 함수의 반환값인 `profiling_mat`가 모든 레이어의 scale
행렬(bf16, 64 experts × 레이어당 ~1.3GB)을 **GPU에 올려둔 채로** 계속
쌓아가다가 함수가 끝날 때 한 번에 `torch.save()`하는 구조였다 — 27개
레이어 전부 끝나면 ~35GB가 GPU에 동시에 쌓이는 셈. **2차 수정:**
`layer_profile[name] = scaling_diag_matrix.to(torch.bfloat16).cpu()` —
계산 직후 CPU로 옮겨서 GPU에는 그 레이어 처리 중에만 머물게 함. 두 수정을
모두 넣고 다시 처음부터 테스트한 결과, 메모리가 27개 레이어 내내 ~34GB
근처에서 안정적으로 유지됐다 (모델 자체 크기+오버헤드 수준, 레이어 수와
무관) — 두 버그 모두 실제 원인이었고, 각각 부분적으로만 고치면 여전히
OOM 났을 것이다.

**2×2 설계: {Fisher calibration 언어} × {Scale calibration 언어}, 둘 다
{EN, KO}.** KO를 고른 이유는 이미 placebo로 가장 견고하게 검증된 own-language
효과(Fisher 단독, +5.598%p)를 가진 언어라 whitening이 그 효과를 증폭/상쇄/
지배하는지 볼 기준점이 되기 때문. `phase1_run_freq_and_scale.py
--include-scale`가 이미 Fisher와 동일한 방식(우리 calibration pool을
monkeypatch)으로 get_scale.py를 돌리므로, "Scale=KO"는 Fisher 계산에 쓴 것과
**동일한 korean_only calibration 텍스트**를 재사용한다(같은 seed).

**사전 등록 (실행 전, 결과 확인 전 기록):**

- 4셀: (Fisher=EN,Scale=EN) / (Fisher=EN,Scale=KO) / (Fisher=KO,Scale=EN) /
  (Fisher=KO,Scale=KO). Fisher는 english_only/korean_only의 기존 seed0 데이터
  재사용, Scale은 이번에 새로 계산(seed0, 64 samples/seqlen 512 — Fisher와
  동일 예산).
- **핵심 비교 (Fisher=KO 고정, Scale만 변경):** `own_scale_gain(KO) =
  bpb_increase(Fisher=KO,Scale=EN,KO 평가) − bpb_increase(Fisher=KO,Scale=KO,
  KO 평가)`. 이 값이 Fisher 단독 결과(+5.598%p)보다 **크면 whitening이
  주범**(Fisher보다 더 큰 영향), **작으면 Fisher가 주범**(whitening은
  부차적).
- **보조 비교 (Fisher=EN 고정, Scale만 변경):** 같은 계산을 Fisher=EN에서도
  반복 — whitening 효과가 Fisher 계산 언어와 무관하게 일관된 크기로
  나타나는지(경로 독립성) 확인.
- seed는 1개로 시작(탐색적 mechanism 진단 — 주 결과가 아니므로 Phase 1
  본 실험만큼의 seed 반복은 이번 라운드에 요구하지 않음, 신호가 애매하면
  추가 seed 검토).

**세 번째, 별개의 버그 — 메모리와 무관, 아직 미해결.** 1)/2)번 메모리 수정을
검증하려고 작은 예산(4 samples, seqlen 128)으로 27개 레이어 전체를 통과하는
테스트를 두 번 돌렸는데(각각 device 변수 섀도잉 수정 전/후), **두 번 다
정확히 같은 지점(레이어 13, 경과 시간 약 7분 6~7초)에서 동일하게 크래시**
났다 — seed=0 고정이라 완전히 결정론적으로 재현된다. 이번엔 메모리 문제가
아니다: 실제 traceback을 보면

```
modeling_deepseek.py, line 413, in moe_infer
```

**DeepSeek 자체 vendored 모델 코드의 `moe_infer`(expert routing 결과를
모으는 scatter_reduce_ 연산) 안에서 나는 에러다** — get_scale.py의 자체
루프(1)/2)에서 고친 부분들)이나 이번에 고친 device 변수 섀도잉과는 무관한
지점. Phase 1의 real Fisher 계산(`phase1_fisher.py`)은 같은 모델·비슷하거나
더 다양한 calibration 텍스트로 EN/KO/ZH/Swahili 전부 27개 레이어를 문제없이
통과했는데, 그건 `model(input_ids=..., labels=...)`로 표준 forward를
호출하는 반면, get_scale.py는 `layer(inps[j].unsqueeze(0))[0]`로 **레이어를
한 번에 하나씩, 샘플을 한 번에 하나씩(batch_size=1 고정), attention_mask 없이
직접 호출**하는 완전히 다른(비표준) 메커니즘을 쓴다 — 이 차이가 원인일
가능성이 높다. 정확한 근본 원인(어떤 인덱스가 범위를 벗어나는지)은
`CUDA_LAUNCH_BLOCKING=1`로 동기 traceback을 받아야 특정할 수 있는데, 아직
안 함.

**판단:** 여기서 메모리 누수 2건은 실제로 고쳤고(검증 완료, 예전 OOM
지점인 레이어 6개를 훨씬 넘어 레이어 13까지 안정적으로 진행), 이번 세
번째 버그는 성격이 다르다 — vendored 모델 코드의 데이터-의존적 인덱싱 버그로
보인다. 사용자에게 세 가지 선택지(더 깊이 디버깅 / CUDA_LAUNCH_BLOCKING=1로
정밀 진단 / 지금은 보류)를 물었고, **"자체 재구현"을 선택** — vendored
get_scale.py를 더 고치는 대신, 이미 27개 레이어 전체를 EN/KO/ZH/Swahili
전 조건에서 문제없이 통과해온 `phase1_fisher.py`의 표준 forward 메커니즘
(`model(input_ids=...)`)을 재사용해서 같은 통계(scaling_diag_matrix = X^T X
누적)를 처음부터 다시 짜기로 했다.

**`scripts/phase1_svd_scale.py` — 재구현 완료, 스모크 테스트 통과.**
`phase1_fisher.py`의 `build_samples`/`MOE_LAYERS`를 그대로 재사용하고,
레이어별로 hook을 걸어 각 expert의 gate/up/down_proj 입력을 CPU에 fp64로
누적(get_scale.py의 두 번째 누수와 같은 이유로 CPU에 유지) → 대칭화 →
eigenvalue clamp → Cholesky(get_scale.py와 동일한 수식, GPU에서 처리 후
결과만 CPU로 복귀 — 순수 CPU eigh/cholesky는 2048×2048 행렬 192개 기준
레이어당 ~60초로 느려서 GPU로 되돌림, ~48초로 소폭 개선). Fisher와 달리
backward가 필요 없어 `@torch.no_grad()`로 처리하고 freeze/unfreeze 로직도
없앴다. 출력은 get_scale.py와 동일한 키 형식
(`"mlp.experts.<e>.gate_proj"` 등)이라 `merge_experts()`에 그대로 꽂힌다.
스모크 테스트(4 samples, seqlen 128, 2개 레이어) 통과 확인 후 실제
64×512 예산으로 EN/KO 2조건 + 4셀 merge+eval 실행
(`run_phase1_2x2.py`, `phase1_run_freq_and_scale.py --include-scale`
대신 이 스크립트를 부른다).

### 2.6) Fisher-merge lossless 단위 테스트 — 완료 (2026-07-27)

**질문:** 지금까지 관측된 언어별 gain/차이가 (a) D2MoE delta-SVD 분해
구현 자체의 버그인지, 아니면 (b) `delta_ratio=0.8` 압축이 정상적으로
걸려서 나오는 진짜 언어 효과인지 — 사용자 요청으로 독립 검증.

**시도 1 (실패, 자원 문제):** `phase1_merge_eval.py --delta-ratio 2.0`으로
27개 레이어 전체를 무손실(rank≥full_rank) 설정으로 merge 시도 → OOM.
원인 규명: `svd_delta`의 `ratio`→rank 변환 공식이
`num_s = dim0×dim1×ratio/(dim0+dim1)`라서, `ratio=1.0`은 full rank가
아니라 rank=834(full=1408)에 불과함 — full rank 도달에는 `ratio≥1.6875`
필요. 근데 rank가 min(dim)=1408에 가까워지면 U+V 저랭크 분해가 원본
dense 행렬보다 **더 많은 파라미터**를 씀(계산 결과: rank=1408일 때
U+V 파라미터가 원본의 1.69배) → 27레이어 전체 full-rank화 시 delta
가중치만 50.5GB, GPU 2장(44GiB) 예산 초과. **이건 파이프라인 버그가
아니라 저랭크 분해의 수학적 성질이 만든 자원 문제.**

**시도 2 (성공):** `phase1_lossless_unit_test.py` 신규 작성 — 27개
레이어 전체 대신 레이어 1개(레이어 5, condition=english_only seed0의
기존 캐시된 Fisher 재사용)만 `delta_ratio=2.0`(실제 사용 rank=1668,
full_rank 1408 이상)으로 merge하고, 원본 expert 가중치(merge 전 clone)와
재구성 가중치(`Wmean + delta_u @ delta_v` — `merge_deepseek.py`의
`forward()`/`probe_process()`가 실제 쓰는 것과 동일한 조합식)를 직접
비교. 결과 (192개 (projection,expert) 쌍 전부):

  - mean relative Frobenius error = **0.303%**
  - max relative Frobenius error = **0.309%**
  - max abs element error = 0.00143

bf16 반올림 오차 수준(통상 ~0.4%)과 일치 → **LOSSLESS 확인, delta 분해
수학 자체는 버그 없음.** 이전에 확인한 (1) `delta_ratio=0.8`이 실제로
rank=667로 진짜 압축을 거는지(no-op 아님), (2) calibration/eval 인덱스
분리(leakage 없음), (3) own-Scale-language 보호 패턴이 두 독립 Fisher
조건에서 재현되는 것과 종합하면: 지금까지 관측된 언어별 gain 차이는
구현 버그가 아니라 **`delta_ratio=0.8` 압축 하에서 나오는 진짜 언어
효과**라는 결론을 뒷받침. (다만 이건 구조적/코드 레벨 반증이고, whitening
효과의 통계적 확정은 여전히 2.5)의 seed+placebo gate 결과가 담당.)

결과 파일: `/mnt/HDD/minjeong/d2moe_results/phase1/phase1_lossless_unit_test_result.json`

### 3) EN 역설 진단 — 1번(bpb 재계산)으로 상당 부분 재해석됨

per-token 기준으로 봤던 "EN-only가 macro 최선"이라던 반직관적 결과는 bpb로
보면 이미 많이 좁아졌다(EN-only macro 16.7%, 4개 조건 중 2위, Balanced와

### 1.7) 저자원 언어(Swahili) 추가 — 완료 (2026-07-25, GPU 4장 병렬)

사용자 지적에 따라 whitening(2번)보다 먼저 순서를 당겼다: KO의
own-language 효과가 placebo로 검증됐지만(1.6번) "KO 한 언어의 사례"일 뿐이라
저자원 언어를 추가해야 패턴인지 확인된다는 지적. 스와힐리어(swh_Latn,
FLORES-parallel에 있음)를 사용자가 선택했다.

**4 GPU 병렬 실행 (사용자 요청 — "5시간 이내로 gpu 4장 다 써서").** 평소
`MAX_GPUS=2` 정책을 이번만 임시로 풀어서, `nvidia-smi`로 4장 전부 유휴임을
재확인한 뒤 GPU를 (0,1)/(2,3) 두 쌍으로 나눠 `run_phase1_swahili.py --stream
a`/`--stream b`를 동시에 백그라운드 실행했다. 각 커맨드 실행 직전에도
Python으로 safe_gpus.sh와 동일한 소유권 검사를 다시 수행(요청받은 GPU
페어가 실제로 안전한지, 두 스트림이 서로 다른 GPU를 쓰기로 한 약속을
어기지 않는지). 6개 run(swahili_only/swahili_only_b 각 3 seed) +
english_only 3 seed의 "eval-only 재실행"(이미 계산된 Fisher/freq 파일을
재사용해서 merge+eval만 다시 돌려 Swahili 평가를 추가 — freq+fisher
재계산 없이 English의 "기본 calibration" 참조점을 저렴하게 확보) + baseline
재평가(Swahili 필드 추가)로 구성. 총 소요 **3시간 50분** (17:18~21:08),
목표(5시간) 안에 여유 있게 완료, 에러 없음.

**결과 (`scripts/phase1_swahili_gate.py`, 사전 등록 기준 그대로 적용):**

```
baseline swh bpb: 2.2429
per-seed english_only swh increase %: [21.043, 21.914, 20.404]
per-seed swahili_only swh increase %: [13.507, 13.511, 12.809]
per-seed own_gain (english - swahili): [7.536, 8.403, 7.596]
mean own_gain: 7.845%p   relative_gain: 37.14%

per-seed |swahili_only - swahili_only_b| diff: [0.331, 0.155, 0.535]
noise_floor(max): 0.535%p   threshold(2x): 1.069%p
VERDICT: SUPPORTED

vs KO: own_gain 7.845%p > KO's 5.598%p (abs EXCEEDS)
vs KO: relative_gain 37.14% > KO's 24.23% (rel EXCEEDS)
VULNERABILITY-PROPORTIONAL HYPOTHESIS: SUPPORTED
```

**"취약도-비례" 가설이 사전 등록 기준 그대로 지지됐다.** 스와힐리어의
own-language 이득(7.845%p, 상대 37.14%)이 절대·상대 두 척도 모두 KO
(5.598%p, 24.23%)를 넘어서고, 자체 placebo 대비로도 noise floor(0.535%p)의
2배 기준(1.069%p)을 약 14.6배 초과한다 — KO보다도 더 결정적인 신호다.
"압축에 더 취약한(사전학습 데이터가 적은) 언어일수록 own-language
calibration의 실질 효과가 크다"는 이제 **두 번째 독립 데이터 포인트로
확인된 패턴**이지, KO 하나의 예외적 사례가 아니다.

baseline swh bpb 자체(2.2429)도 EN(0.91)/KO(1.37)/ZH(1.08)보다 훨씬 높아
— 압축 전부터 이 모델이 스와힐리어를 가장 못한다는 뜻이고, 이게 "가장
취약한 언어일수록 자기 언어 calibration 효과가 크다"는 패턴과 정확히
들어맞는다.

**미룬 것 (의도적):** pp_ratio(2번 끝날 때까지 고정 배제), Qwen3 포팅(Phase 2
후보, 04_전체요약.md "다음 단계"에 남겨둠), downstream task(Belebele 등, PPL
신호 안정화 이후).
